# C 接口复用 Python 推理核心方案

日期：2026-09-21

## 1. 决策

不再把 Python `massnova` 算法逐项重写到 C++。Python 推理核心是候选峰、边界、信号门控、去重和评分的唯一实现；C DLL 只保留既有 ABI、任务生命周期和 Python 引擎桥接。

目标结构：

```text
MassNova 后端
  -> 既有 qf_* C API
mrmpformer.dll
  -> 输入校验、异步任务、回调、内存所有权、引擎通信
Python runtime engine
  -> massnova_core（唯一算法实现）
  -> ONNX Runtime
mrmpformerv2.onnx
```

后端不接触 Python API，也不需要理解候选峰算法。`mrmpformer.dll` 对后端保持既有函数和 JSON 结构。

## 2. 推荐部署方式

优先使用“常驻 Python sidecar 引擎进程”，而不是在 MassNova 主进程中嵌入 CPython：

- 通过 Nuitka/PyInstaller 等生成 `mrmpformer_engine.exe`；
- `qf_init()` 启动或连接一个隐藏的常驻引擎；
- 引擎只加载一次 Python 模块和 ONNX Session；
- DLL 与引擎通过命名管道或长度前缀二进制协议通信；
- `qf_shutdown()` 关闭引擎；
- 对后端仍表现为同一个 C API。

原因：NumPy、SciPy、Matplotlib、ONNX Runtime 及其 OpenMP/CUDA 依赖直接加载进宿主软件进程，容易发生 DLL、GIL、运行库和崩溃隔离问题。sidecar 可以将这些依赖和故障隔离，同时仍复用 Python 原逻辑。

如果部署环境明确禁止子进程，备选方案才是 DLL 内嵌 CPython。算法层设计不变，只替换桥接实现。

## 3. Python 单一推理接口

新增一个不依赖 mzML 文件和 CLI 的数组接口，例如：

```python
initialize(model_path: str, config: dict) -> None
process_channels(items: list[dict]) -> dict
shutdown() -> None
```

单通道输入：

```python
{
    "uid": str,
    "name": str,
    "channel": str,
    "mzq1": float,
    "mzq3": float,
    "rt": float64[],
    "intensity": float64[],
}
```

输出直接生成既有 C JSON：

```json
{
  "items": [
    {
      "uid": "...",
      "status": "ok",
      "peaks": [
        {"a": 7.621234, "b": 7.913456, "c": 0.932145}
      ],
      "alerts": []
    }
  ]
}
```

Python生成最终 `a/b/c` 后，C层不得再次修边界、重新评分或去重，只校验结果并原样返回。

## 4. Python代码重构

将当前分散在以下文件中的核心算法提取为纯数组模块 `inference/massnova_core.py`：

- `inference/massnova.py`：候选枚举、两遍精修、门控、去重、最终指标；
- `inference/two_round_detection.py`：边界调整及其辅助函数；
- `utils/xic_peak_utils.py`：局部 SNR 和基线；
- `utils/peak_scores.py`：信号峰和统一峰分；
- `preprocessing/xic_extraction.py`：400×300候选窗口渲染。

核心模块不得依赖：

- mzML路径；
- pyOpenMS；
- pandas报表；
- CLI参数解析；
- 测试输出目录和画图报告。

保留 NumPy、SciPy、Matplotlib/Pillow 和 ONNX Runtime，这些决定当前数值行为。

现有 Python CLI 和新的数组接口必须同时调用 `massnova_core`，不允许复制一份算法代码。

## 5. Python中统一使用 ONNX

当前 Python massnova 默认用 PTH/torch，C端用ONNX。为了数值一致，生产Python核心改为使用：

```text
checkpoint/mrmpformerv2.onnx
```

新增内存ONNX预测器：

1. 复用当前Python候选窗口渲染；
2. JPEG按当前方式读取为RGB 0～255；
3. 批量组成 `[B,3,300,400] float32`；
4. ONNX内部完成 `/255` 和 Normalize；
5. 读取 `scores/boxes_xyxy/boxes_norm`；
6. 使用与Python当前相同的 `score > 0.6`、峰顶落框和贪心选择。

这样 C桥接路径和Python CLI使用同一ONNX、同一候选、同一图像、同一后处理。

## 6. C DLL保留的逻辑

保留：

- `qf_default_config/qf_init/qf_shutdown`；
- `qf_process/qf_process_single`；
- 任务ID、异步队列、超时、取消和进度；
- callback；
- 输入指针复制和有限数/严格递增检查；
- `qf_get_result_json/qf_get_result_path/qf_free`；
- 错误码和线程局部错误信息；
- Python引擎启动、握手、通信、崩溃检测和重启策略。

C层可以检查Python返回JSON结构，但不能修改峰结果。

## 7. C DLL移除或停用的私有算法

从生产路径移除：

- `smooth_signal()`；
- `render_roi()`；
- `pixel_to_rt()`；
- `refine_detection()`；
- `find_signal_fallback()`；
- C端阈值过滤和query解释；
- C端模型峰排序以外的业务处理；
- C端 `status=review` 信号兜底规则。

ONNX Session也由Python引擎持有，C DLL不再直接运行模型。原C实现可先保留在非生产编译单元中用于回滚，完成验收后再删除。

## 8. IPC协议

避免用巨大JSON传输 RT/强度数组。建议使用长度前缀二进制帧：

```text
header: magic/version/request_id/item_count
每个item: 字符串长度+UTF-8元数据+n_points+float64 RT+n_points float64 intensity
```

响应可直接使用UTF-8 JSON，因为结果体积较小。协议必须包含：

- bridge协议版本；
- Python核心版本；
- ONNX SHA-256；
- 请求ID；
- 成功/失败状态和错误文本。

`qf_init()` 握手时校验版本和模型hash，避免DLL、Python核心和ONNX错配。

## 9. 后端接口兼容性

不改变：

- `mrmpformer.h` 中已有结构布局和函数签名；
- 后端传入 RT/强度的方式；
- 后端任务等待、回调和结果释放方式；
- `items[].peaks[].a/b/c` 结构。

行为变化需要通知后端：

- `peaks[]` 可能超过3个；
- 信号规则峰也以 `status=ok` 返回；
- `c` 是统一峰自身分：模型峰为Softmax，信号峰为工程分；
- 生产包增加 `mrmpformer_engine` 及其运行时依赖。

## 10. 发布包

推荐：

```text
mrmpformer_sdk/
  include/mrmpformer.h
  bin/mrmpformer.dll
  bin/mrmpformer_engine.exe
  runtime/...
  model/mrmpformerv2.onnx
  manifest.json
```

后端只链接/加载 `mrmpformer.dll`。DLL负责定位其相对目录下的engine和ONNX。`.pth`不进入生产包。

## 11. 验收

1. Python CLI和数组接口对同一通道输出完全一致；
2. DLL桥接返回的JSON数值与数组接口一致；
3. 候选索引、峰数量、排序和来源完全一致；
4. CPU路径最终 `a/b/c` 量化到6位小数后完全一致；
5. test1、test2、test3全量回归；
6. 覆盖宽峰、开叉峰、肩峰、深谷双峰、单通道超过3峰和无模型命中的信号峰；
7. 测试引擎崩溃、超时、取消、软件退出和并发请求；
8. 验证软件安装目录包含全部运行时依赖且不依赖开发机Conda环境。

## 12. 实施顺序

1. 提取并测试 `massnova_core`，现有CLI保持结果不变；
2. 增加ONNX数组运行接口，Python CLI与数组接口共享同一路径；
3. 打包常驻engine并验证无需Conda环境；
4. 将C任务执行替换为engine桥接，公共API不变；
5. 完成数值一致性和故障测试；
6. 形成新SDK包后再交付后端，旧DLL保留可回滚版本。
